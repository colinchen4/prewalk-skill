# Navigator-Builder handoff packages (native DeepSeek executor)

Fill every bracket from observed evidence. Remove optional fields that truly do not apply. Keep prompts self-contained but compact; summarize large diffs instead of pasting them.

## Navigator to Builder

Pass this text to the DeepSeek executor process. If dispatch is unavailable, return it in one fenced block so a new task can resume without repeating Navigator prewalk.

HANDOFF_ID: [short unique ID generated by Navigator]

You are the native DeepSeek subagent acting at the Builder execution boundary. The Navigator prewalk is complete. Do not invoke or repeat the prewalk, do not re-plan from scratch, and continue beyond the first-edit boundary. Work in the existing shared repository and preserve unrelated changes.

OBJECTIVE
[User-visible outcome and acceptance criteria]

REPOSITORY AND BASELINE
- Root: [repository root]
- Branch/commit if known: [value]
- Inherited dirty-worktree state: [relevant pre-existing changes]
- Applicable repository instructions: [AGENTS.md constraints]

NAVIGATOR EVIDENCE
- Entry points and symbols: [paths and symbols]
- Runtime/data flow traced: [concise chain]
- Root cause or implementation direction: [evidence-backed conclusion]
- Evidence observed: [tests, logs, reproduction, compiler output]
- Hypotheses ruled out: [important negative evidence]
- Compatibility constraints and risks: [list]
- Visual facts supplied by Navigator: [text description, paths, dimensions, or not applicable]

DELEGATION BOUNDARY
- Decisions Navigator retained: [plan, requirement/ambiguity interpretation, architecture, correctness-critical choices, final review — name the specifics for this task]
- Executor scope: [mechanical implementation, builds and tests, debugging; include hard-but-mechanical work]
- Escalate only if: [expected ambiguity or direction points, or "none identified"]

MODEL AND EFFORT SELECTION
- Requested Navigator model / effort: [values the user asked for, or the defaults]
- Verified effective Navigator model / effort: [parent session actually in use, with how it was verified]
- Requested executor model / effort: [values the user asked for, or the managed defaults]

- Validation evidence: [commands and observed status/config output; never credentials]

FIRST CREDIBLE EDIT ALREADY LANDED
- Changed paths: [paths]

- Diff summary: [concise summary]
- Focused check already run: [command and exact outcome, or not run]

TODO TRAJECTORY
- [status] [item and its validation]
- [status] [item and its validation]
- [status] [item and its validation]
[Keep 3-8 total items and exactly represent current state]

EXECUTION INSTRUCTIONS
1. Inspect the retained diff and evidence first; reopen files only as required.
2. Complete the remaining TODO items, implementation, debugging, and validation.
3. If repository evidence contradicts this handoff, update the approach and record why.
4. Inspect the final complete diff and preserve unrelated worktree changes.
5. Do not stop at the first failed validation; diagnose it unless genuinely blocked.
6. Treat ordinary implementation, compile, and test failures as your own work; they are not escalation.
7. Escalate only for a genuinely unresolved requirement ambiguity or a new lead-level direction decision. Preserve existing work and return the standard SOL_REVIEW package with state `escalated`, the evidence, the options considered, the smallest safe default, and the exact decision required instead of guessing.
8. Do not perform final approval or Navigator review.

MANDATORY RETURN TO NAVIGATOR
When finished or blocked, your final response must contain a concise status followed by one fenced, copy-ready package beginning exactly with `PREWALK_PHASE: SOL_REVIEW`. It must contain:
- The unchanged `HANDOFF_ID` from this package
- Original objective and acceptance criteria
- Completion or blocked status (`escalated` when a decision is required)
- The decisions Navigator retained and any decision required from Navigator
- The model/effort selection carried forward from this package (requested and validated values) and any deviation; do not assert a model identity beyond those values
- Inherited Navigator first edit and every final changed path
- Important implementation decisions and deviations from the handed-off trajectory
- Exact test/build/lint commands and outcomes
- Remaining failures, warnings, risks, and unverified areas
- Baseline/diff range Navigator should inspect
- An instruction for Navigator to review actual code and diff rather than trust the summary

Do not review or approve your own implementation. Return control to the parent Navigator agent.
```

ORIGINAL OBJECTIVE
[User-visible outcome and acceptance criteria]

EXECUTION STATUS
- State: [complete | partially complete | blocked | escalated — `escalated` means a decision belongs to Navigator]

- Review baseline/diff range: [starting commit, branch, or precise comparison]
- Inherited unrelated worktree changes: [list]
- Model/effort selection carried forward: [requested and effective Navigator values; requested and validated executor launch values; any deviation]

CHANGE TRAJECTORY
- Navigator first edit: [paths and summary]
- Final changed paths: [complete inventory]
- Decisions Navigator retained: [list from the handoff; note any the executor crossed]
- Implementation decisions: [key decisions and rationale]
- Deviations from Navigator handoff: [what changed and why]
- Remaining TODO or blocker: [none or exact items]

VALIDATION EVIDENCE
- [command]: [exit status and concise result]
- [command]: [exit status and concise result]
- Failures/warnings: [exact outstanding issues]
- Not run or unverified: [explicit gaps]

KNOWN RISKS
- [edge case, compatibility, security, migration, concurrency, or operational risk]

REVIEW INSTRUCTIONS
1. Inspect repository instructions, worktree status, and the actual diff against the stated baseline.
2. Verify requirement coverage and that the implementation addresses the evidenced cause.
3. Check correctness, error paths, compatibility, security, unintended changes, and test adequacy.
4. Verify the carried-forward model/effort selection against the actual launch command and the parent session; do not treat the executor's self-report as proof of its model.
5. Run targeted read-only checks or tests where useful.
6. Report findings by severity with precise file and line references. If there are no findings, state that clearly and list residual risks or tests not performed.
7. Do not edit code unless the user explicitly requests remediation.
```
